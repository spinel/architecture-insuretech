# Задание 2: Динамическое масштабирование контейнеров

## Описание

Данное задание демонстрирует решение проблемы динамического масштабирования для сервисов InsureTech с использованием Kubernetes HPA (Horizontal Pod Autoscaler).

## Проблема

- В периоды пиковой нагрузки система не справляется с обработкой запросов
- Нестабильное поведение и постоянные перезагрузки подов из-за нехватки памяти
- Снижение NPS из-за негативного пользовательского опыта
- Экономическая неэффективность постоянного содержания большого количества реплик

## Решение

Использование HPA для автоматического масштабирования подов на основе метрик CPU и памяти.

## Компоненты

### 1. scaletestapp-deployment.yaml
- Deployment для тестового приложения
- Настроенные ресурсы (requests/limits)
- Health checks (liveness/readiness probes)
- Начальное количество реплик: 2

### 2. scaletestapp-service.yaml
- Service для доступа к приложению
- ClusterIP тип для внутреннего доступа

### 3. scaletestapp-hpa.yaml
- HPA конфигурация
- Минимум: 2 реплики
- Максимум: 10 реплик
- Метрики: CPU (70%) и Memory (80%)
- Настроенное поведение масштабирования

### 4. load-test.sh
- Скрипт для нагрузочного тестирования
- Демонстрирует работу HPA при различной нагрузке

### 5. monitor-scaling.sh
- Скрипт для мониторинга масштабирования
- Отслеживание метрик Prometheus
- Мониторинг состояния HPA

## Развертывание

### Предварительные требования
- Kubernetes кластер
- kubectl настроен для доступа к кластеру
- Metrics Server установлен в кластере

### Шаги развертывания

1. **Развертывание приложения:**
```bash
kubectl apply -f scaletestapp-deployment.yaml
kubectl apply -f scaletestapp-service.yaml
```

2. **Создание HPA:**
```bash
kubectl apply -f scaletestapp-hpa.yaml
```

3. **Проверка развертывания:**
```bash
kubectl get pods -l app=scaletestapp
kubectl get svc scaletestapp-service
kubectl get hpa scaletestapp-hpa
```

4. **Проброс портов для тестирования:**
```bash
kubectl port-forward svc/scaletestapp-service 8080:8080
```

## Тестирование

### Базовое тестирование
```bash
# Проверка доступности
curl http://localhost:8080/

# Проверка метрик
curl http://localhost:8080/metrics
```

### Нагрузочное тестирование
```bash
# Запуск полного теста
./load-test.sh

# Создание нагрузки
./monitor-scaling.sh load 20 60  # 20 RPS в течение 60 секунд

# Мониторинг масштабирования
./monitor-scaling.sh monitor 300 10  # 5 минут каждые 10 секунд
```

### Мониторинг
```bash
# Текущий статус
./monitor-scaling.sh status

# Логи подов
./monitor-scaling.sh logs

# Ручной мониторинг
kubectl get hpa scaletestapp-hpa -w
kubectl top pods -l app=scaletestapp
```

## Ожидаемое поведение

### При увеличении нагрузки:
1. CPU и Memory utilization растут
2. HPA обнаруживает превышение порогов
3. Количество реплик увеличивается (до 10)
4. Нагрузка распределяется между подами
5. Метрики стабилизируются

### При снижении нагрузки:
1. CPU и Memory utilization падают
2. HPA обнаруживает снижение нагрузки
3. Количество реплик уменьшается (до 2)
4. Ресурсы освобождаются

## Конфигурация HPA

### Метрики масштабирования:
- **CPU**: 70% utilization
- **Memory**: 80% utilization

### Поведение масштабирования:
- **Scale Up**: 
  - Стабилизация: 60 секунд
  - Максимум: 50% или 2 пода за 60 секунд
- **Scale Down**:
  - Стабилизация: 300 секунд
  - Максимум: 10% за 60 секунд

### Ограничения:
- Минимум реплик: 2
- Максимум реплик: 10

## Мониторинг и метрики

### Kubernetes метрики:
- `kubectl get hpa` - статус HPA
- `kubectl top pods` - использование ресурсов
- `kubectl describe hpa` - детальная информация

### Prometheus метрики:
- `http_requests_total` - количество HTTP запросов
- `go_goroutines` - количество горутин
- `go_memstats_*` - статистика памяти

## Устранение неполадок

### HPA не масштабируется:
1. Проверить установку Metrics Server
2. Проверить ресурсы requests/limits в Deployment
3. Проверить метрики: `kubectl top pods`

### Поды не запускаются:
1. Проверить логи: `kubectl logs <pod-name>`
2. Проверить события: `kubectl get events`
3. Проверить ресурсы кластера

### Медленное масштабирование:
1. Настроить behavior в HPA
2. Уменьшить stabilizationWindowSeconds
3. Проверить интервал сбора метрик

## Результаты

После успешного развертывания и тестирования:

1. **Автоматическое масштабирование** работает корректно
2. **Ресурсы используются эффективно** - масштабирование только при необходимости
3. **Пользовательский опыт улучшается** - нет перегрузок системы
4. **Экономическая эффективность** - оплата только за используемые ресурсы

## Применение к InsureTech

Данное решение может быть применено к реальным сервисам InsureTech:

1. **core-app** - основное приложение
2. **client-info** - сервис клиентских данных
3. **ins-product-aggregator** - агрегатор продуктов
4. **ins-comp-settlement** - сервис взаиморасчетов

Каждый сервис получит индивидуальную конфигурацию HPA в зависимости от его характеристик нагрузки.
