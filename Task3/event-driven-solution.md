# Event-Driven архитектура для InsureTech

## Обзор решения

### Цель
Переход от синхронной REST-архитектуры к асинхронной Event-Driven архитектуре для обеспечения масштабируемости, отказоустойчивости и производительности при росте до 10 страховых компаний.

## Ключевые компоненты Event-Driven архитектуры

### 1. Message Broker - Apache Kafka
**Выбор**: Apache Kafka
**Обоснование**:
- Высокая производительность и пропускная способность
- Горизонтальное масштабирование
- Гарантированная доставка сообщений
- Поддержка множественных консьюмеров
- Встроенная репликация и отказоустойчивость

### 2. Event Store - Apache Kafka Topics
**Структура топиков**:
- `insurance.products.updated` - обновления тарифов страховых компаний
- `insurance.policies.created` - создание новых страховок
- `insurance.policies.updated` - обновления статуса страховок
- `insurance.settlements.required` - требования к взаиморасчётам
- `insurance.companies.status` - статус доступности страховых компаний

## Архитектурные решения

### 1. Взаимодействия для перевода на Event-Streaming

#### 1.1 Обновление тарифов страховых компаний
**Текущее взаимодействие**: 
- ins-product-aggregator → страховые компании (синхронно)
- core-app → ins-product-aggregator (каждые 15 минут)
- ins-comp-settlement → ins-product-aggregator (раз в сутки)

**Event-Driven решение**:
- ins-product-aggregator → Kafka Topic `insurance.products.updated`
- core-app ← Kafka Consumer (в реальном времени)
- ins-comp-settlement ← Kafka Consumer (в реальном времени)

#### 1.2 Создание страховок
**Текущее взаимодействие**:
- core-app → ins-comp-settlement (раз в сутки, REST)

**Event-Driven решение**:
- core-app → Kafka Topic `insurance.policies.created`
- ins-comp-settlement ← Kafka Consumer (в реальном времени)

#### 1.3 Взаиморасчёты со страховыми компаниями
**Текущее взаимодействие**:
- ins-comp-settlement → страховые компании (синхронно)

**Event-Driven решение**:
- ins-comp-settlement → Kafka Topic `insurance.settlements.required`
- Отдельный сервис Settlement Processor ← Kafka Consumer
- Settlement Processor → страховые компании (асинхронно)

### 2. Паттерн Transactional Outbox

#### 2.1 Применение паттерна
**Где используется**:
- core-app: при создании страховок
- ins-product-aggregator: при обновлении тарифов
- ins-comp-settlement: при формировании взаиморасчётов

#### 2.2 Реализация
**Компоненты**:
1. **Outbox Table** в каждой базе данных
2. **Outbox Publisher** - сервис для публикации событий
3. **Event Sourcing** - сохранение истории событий

**Схема работы**:
```
1. Бизнес-транзакция в основной таблице
2. Запись события в Outbox Table (в той же транзакции)
3. Outbox Publisher читает события и публикует в Kafka
4. Удаление обработанных событий из Outbox Table
```

#### 2.3 Преимущества
- **Консистентность**: Гарантия публикации события при успешной бизнес-транзакции
- **Надёжность**: Отсутствие потери событий
- **Производительность**: Асинхронная публикация не блокирует бизнес-операции

### 3. Кэширование и репликация данных

#### 3.1 Redis Cache
**Назначение**:
- Кэширование актуальных тарифов страховых компаний
- Хранение статуса доступности страховых компаний
- Кэширование клиентских данных

**Структура**:
- `tariffs:{company_id}` - тарифы по компаниям
- `tariffs:all` - агрегированные тарифы
- `companies:status` - статус доступности компаний

#### 3.2 Репликация данных
**Механизм**:
- Event-driven обновление кэша при получении событий
- TTL для автоматической инвалидации устаревших данных
- Fallback на базу данных при отсутствии в кэше

## Детальная архитектура сервисов

### 1. ins-product-aggregator (Event-Driven версия)

#### 1.1 Функциональность
- **Scheduler Service**: Периодический опрос страховых компаний
- **Event Publisher**: Публикация обновлений тарифов
- **Health Checker**: Мониторинг доступности страховых компаний

#### 1.2 Event Flow
```
1. Scheduler запускает опрос страховых компаний
2. Получение данных от каждой компании (параллельно)
3. Агрегация и валидация данных
4. Сохранение в базу данных + Outbox Table
5. Публикация события insurance.products.updated
6. Обновление кэша Redis
```

### 2. core-app (Event-Driven версия)

#### 2.1 Функциональность
- **Event Consumer**: Подписка на обновления тарифов
- **Event Publisher**: Публикация событий создания страховок
- **Cache Manager**: Управление локальным кэшем

#### 2.2 Event Flow
```
1. Получение события insurance.products.updated
2. Обновление локального кэша тарифов
3. При создании страховки:
   - Сохранение в базу данных + Outbox Table
   - Публикация события insurance.policies.created
```

### 3. ins-comp-settlement (Event-Driven версия)

#### 3.1 Функциональность
- **Event Consumer**: Подписка на события создания страховок
- **Settlement Processor**: Обработка взаиморасчётов
- **Event Publisher**: Публикация требований к взаиморасчётам

#### 3.2 Event Flow
```
1. Получение события insurance.policies.created
2. Накопление данных для взаиморасчётов
3. По расписанию (раз в сутки):
   - Формирование реестра взаиморасчётов
   - Публикация события insurance.settlements.required
```

### 4. Новый сервис: Settlement Processor

#### 4.1 Функциональность
- **Event Consumer**: Обработка требований к взаиморасчётам
- **Company Integrator**: Интеграция со страховыми компаниями
- **Retry Manager**: Управление повторными попытками

#### 4.2 Event Flow
```
1. Получение события insurance.settlements.required
2. Параллельная отправка данных в страховые компании
3. Обработка ответов и ошибок
4. Retry при неудачных попытках
5. Публикация результатов взаиморасчётов
```

## Преимущества Event-Driven архитектуры

### 1. Масштабируемость
- **Горизонтальное масштабирование**: Каждый сервис масштабируется независимо
- **Параллельная обработка**: Множественные консьюмеры для одного топика
- **Load Balancing**: Автоматическое распределение нагрузки

### 2. Отказоустойчивость
- **Изоляция сбоев**: Сбой одного сервиса не влияет на другие
- **Retry механизмы**: Автоматические повторные попытки
- **Dead Letter Queue**: Обработка проблемных сообщений

### 3. Производительность
- **Асинхронность**: Неблокирующие операции
- **Кэширование**: Быстрый доступ к актуальным данным
- **Batch обработка**: Группировка операций для эффективности

### 4. Гибкость
- **Loose Coupling**: Слабая связанность между сервисами
- **Event Sourcing**: Полная история изменений
- **Easy Integration**: Простое добавление новых сервисов

## Мониторинг и наблюдаемость

### 1. Метрики Kafka
- Пропускная способность топиков
- Задержка обработки сообщений
- Размер очередей консьюмеров

### 2. Метрики сервисов
- Время обработки событий
- Количество успешных/неуспешных операций
- Использование ресурсов

### 3. Алерты
- Превышение задержки обработки
- Накопление сообщений в очереди
- Недоступность страховых компаний

## Заключение

Event-Driven архитектура с использованием Apache Kafka и паттерна Transactional Outbox обеспечит:

1. **Масштабируемость** до 10+ страховых компаний
2. **Отказоустойчивость** при сбоях отдельных компонентов
3. **Производительность** за счёт асинхронной обработки
4. **Гибкость** для добавления новых интеграций

Данное решение устранит все выявленные проблемы текущей архитектуры и подготовит систему к дальнейшему росту.
