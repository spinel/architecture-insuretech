# Анализ REST API сервиса client-info

## Анализ Swagger контракта

### Существующие ресурсы и операции

#### 1. Клиент (`/clients/{id}`)
- **Операция**: `GET /clients/{id}`
- **Описание**: Получение информации о клиенте по ID
- **Возвращает**: Объект `Client`
- **Поля**:
  - `id` (string) - ID клиента
  - `name` (string) - Имя клиента
  - `age` (integer) - Возраст клиента

#### 2. Документы (`/clients/{id}/documents`)
- **Операция**: `GET /clients/{id}/documents`
- **Описание**: Получение списка документов клиента
- **Возвращает**: Массив объектов `Document`
- **Поля документа**:
  - `id` (string) - ID документа
  - `type` (string) - Тип документа
  - `number` (string) - Номер документа
  - `issueDate` (string) - Дата выдачи
  - `expiryDate` (string) - Дата истечения

#### 3. Родственники (`/clients/{id}/relatives`)
- **Операция**: `GET /clients/{id}/relatives`
- **Описание**: Получение информации о родственниках клиента
- **Возвращает**: Массив объектов `Relative`
- **Поля родственника**:
  - `id` (string) - ID родственника
  - `relationType` (string) - Тип родства
  - `name` (string) - Имя родственника
  - `age` (integer) - Возраст родственника

## Проблемы текущего REST API

### 1. N+1 Problem
**Проблема**: Для получения полной информации о клиенте необходимо выполнить 3 отдельных запроса:
```
GET /clients/{id}           - основная информация
GET /clients/{id}/documents - документы
GET /clients/{id}/relatives - родственники
```

**Последствия**:
- Увеличение RPS в 3 раза
- Задержка из-за множественных HTTP-запросов
- Сложность управления состоянием на клиенте

### 2. Over-fetching
**Проблема**: Клиент получает все поля, даже если нужны только некоторые:
- При запросе документов получаем все поля документа
- При запросе родственников получаем все поля родственника

### 3. Under-fetching
**Проблема**: Невозможность получить связанные данные в одном запросе:
- Нельзя получить клиента с его документами в одном запросе
- Нельзя получить клиента с родственниками в одном запросе

### 4. Жёсткая структура
**Проблема**: API не позволяет гибко выбирать нужные поля:
- Всегда возвращаются все поля объекта
- Нет возможности запросить только необходимые поля

## Анализ структуры данных

### Иерархия данных
```
Client (1)
├── Documents (N)
└── Relatives (N)
```

### Связи между сущностями
- **Client → Documents**: One-to-Many
- **Client → Relatives**: One-to-Many
- **Documents → Client**: Many-to-One
- **Relatives → Client**: Many-to-One

## Требования к GraphQL решению

### 1. Устранение N+1 Problem
- Возможность получить клиента с документами и родственниками в одном запросе
- Возможность получить только нужные поля

### 2. Гибкость запросов
- Выбор конкретных полей для каждой сущности
- Возможность запросить связанные данные
- Возможность запросить только необходимые данные

### 3. Производительность
- Снижение количества HTTP-запросов
- Уменьшение объёма передаваемых данных
- Оптимизация загрузки данных

### 4. Обратная совместимость
- Покрытие всех операций REST API
- Сохранение логики получения данных
- Возможность миграции без breaking changes

## Выводы для GraphQL схемы

### Необходимые типы:
1. **Client** - основная сущность клиента
2. **Document** - документы клиента
3. **Relative** - родственники клиента

### Необходимые запросы:
1. **client(id: ID!)** - получение клиента по ID
2. **clients** - получение списка клиентов (для будущего расширения)

### Связи:
- Client должен иметь поля `documents` и `relatives`
- Document и Relative должны иметь поле `client` для обратной связи

### Оптимизации:
- Возможность запросить только нужные поля
- Возможность запросить связанные данные
- Возможность контролировать глубину запроса
